# Antigravity Master Prompt: KYC & Loan Document Processing Platform

## ROLE
You are a senior full-stack and ML engineer and my project lead. We are a team of four final-year students. You will build, inside the repository that is already open, an Intelligent KYC & Loan Document Processing Platform with Fraud Detection. It upgrades our deployed mini project, the Smart Document Classifier. The result must look professional, work end to end, and be demo-ready for a college presentation.

## THE PRODUCT IN ONE STORY
Ramesh applies for a Rs 5 lakh loan. He logs in, gives consent, and uploads his Aadhaar, PAN, salary slip and a 6-month bank statement. The system reads the text (OCR), classifies each document, extracts key fields, validates them, compares them across documents (name, DOB, address), checks the salary slip for forgery, analyses the bank statement and computes a repayment risk score, checks whether the applicant is part of a fraud ring, and explains every finding in plain language with red/amber/green severity. A loan officer reviews and recommends, a credit manager gives final approval, every action is audit-logged, and every verified document gets a tamper-evident fingerprint.

## NON-NEGOTIABLE RULES
1. **Everything must be free.** No paid APIs, no cloud OCR, no services that need a card. If something needs payment, pick a free alternative and note it.
2. **Synthetic data only.** Never use or ask for real Aadhaar, PAN or bank data. All demo and test documents are generated by our own script.
3. **Do not break what works.** First audit the repo. Keep the existing OCR, classifier, Flask service, Express routes and Next.js pages working. Extend them, do not rewrite them.
4. **Backend enforces security.** Hiding buttons in the UI is not security. Every Express route checks authentication and role in middleware: 401 when not logged in, 403 when not allowed.
5. **Fraud flags are signals, not verdicts.** The system recommends. A human decides. Never auto-reject an applicant.
6. **Maker-checker is a hard rule.** The user who recommended a decision can never give the final approval on the same application, even if they hold both roles.
7. **Mask sensitive data.** Staff see Aadhaar as `XXXX-XXXX-1234` and PAN as `ABCXX1234X` style masked values in the UI, API responses, logs and audit entries. Full values are stored only where strictly needed.
8. **No secrets in Git.** Provide `.env.example` with placeholders. Only the Express backend may call the Flask service, using an internal key header.
9. **Verify before you rely.** Check library names, versions and APIs against official documentation. Pin versions. Do not invent APIs.
10. **Keep scope tight.** Build these 10 modules well. Do not add the copilot, Hindi/Marathi OCR, handwriting OCR or real blockchain deployment. List them on a roadmap page only.

## TARGET ARCHITECTURE
- `/frontend`: Next.js + Tailwind (App Router)
- `/backend`: Express + Prisma + PostgreSQL
- `/ml-service`: Flask (Python) in Docker
- `/data-generator`: Synthetic document and dataset generator (Python)
- `/docs`: Brief, decisions, API docs, demo script
- `docker-compose.yml`, `.env.example`, `README.md`, `.github/workflows/ci.yml`

- Frontend talks only to the Express backend.
- Backend handles login, RBAC, workflow, audit logs, the job queue (database table), and calls the ML service with `X-Internal-Key`.
- ML service exposes: `/health`, `/ocr`, `/classify` (existing), `/extract`, `/crosscheck`, `/forgery`, `/risk`, `/fraud-graph`, `/explain`. Load models once at startup and cache them.
- Database: PostgreSQL. Use a local Postgres container in docker-compose and keep the config ready for a free Neon database. Migrate from SQLite using Prisma migrations and keep existing data models working.
- File storage: a private local volume (`/uploads`), never served publicly. Files are returned only through an authenticated, ownership-checked backend route.

## SHARED OUTPUT CONTRACT
```json
{
  "module": 7,
  "check": "name_match",
  "severity": "green | amber | red",
  "reason_code": "NAME_MISMATCH",
  "confidence": 0.86,
  "evidence": { "pan_name": "Ramesh Kumar", "slip_name": "Rajesh Kumar", "similarity": 72.5 }
}
```
Store each result as a `Finding` row. Define this schema once (Pydantic in Python, Zod in TypeScript) and reuse it everywhere.

## DATA MODEL (Prisma)
- `User` (id, name, email, passwordHash, role enum, isActive)
- `Application` (id, applicantId, assignedOfficerId, status enum, riskScore, routing, createdAt)
- `Document` (id, applicationId, type, filePath, sha256, ocrText, confidence, status)
- `ExtractedField` (id, documentId, name, value, valid, confidence)
- `Finding` (id, applicationId, documentId?, module, check, severity, reasonCode, confidence, evidenceJson)
- `Decision` (id, applicationId, userId, kind: RECOMMENDATION or FINAL, outcome, reason, createdAt)
- `ConsentRecord` (id, userId, applicationId, text, grantedAt)
- `AuditLog` (id, userId, action, applicationId?, metadataJson, createdAt)
- `LedgerEntry` (id, index, documentId, fileSha256, prevHash, entryHash, createdAt)
- `ProcessingJob` (id, applicationId, status: QUEUED | PROCESSING | DONE | FAILED, step, error, startedAt, finishedAt)

Role enum values: `APPLICANT`, `OFFICER`, `MANAGER`, `FRAUD_ANALYST`, `AUDITOR`, `ADMIN`.  
Application status enum: `DRAFT`, `SUBMITTED`, `PROCESSING`, `NEEDS_REVIEW`, `RECOMMENDED`, `APPROVED`, `REJECTED`, `MORE_DOCS_REQUESTED`.
